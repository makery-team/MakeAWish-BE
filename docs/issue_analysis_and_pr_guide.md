# 🚨 장애 분석 리포트 및 PR 작성 가이드

이 문서는 기존에 잘 작동하던 서버가 왜 갑자기 AWS 환경에서 500 에러를 뱉으며 뻗어버렸는지, 그리고 AI 연동이 왜 실패했는지를 낱낱이 파헤친 리포트입니다. 팀원들과 공유하시면 현재 서버 상태를 완벽하게 이해하실 수 있습니다.

---

## 1. 🔍 사건의 재구성 (왜 갑자기 다 터졌는가?)

사건의 발단은 `da39c97` 시절로 거슬러 올라갑니다.

### ① 첫 번째 불씨: `data.sql`의 JSON 문법 에러
* 처음 AWS에 배포되었을 때(`da39c97`), 사실 `data.sql` 안에서 MySQL JSON 문법 에러가 나고 있었습니다.
* 그래서 겉보기엔 서버가 켜져 있었지만, **실제 DB에는 상품(Product), 유저(User) 등 핵심 초기 데이터가 하나도 들어가지 않은 텅 빈 '깡통 DB' 상태**였습니다.

### ② 두 번째 불씨: DB 초기화 잠금 (`f19b2bf`)
* 다행히 팀원분께서 `data.sql`의 JSON 에러를 발견하고 올바르게 고치셨습니다!
* **하지만 동시에**, 실서버 DB 데이터를 보호하기 위해 `application.yml`에서 DB 초기화 설정을 꺼버리셨습니다. (`sql.init.mode: never`)
* **결과:** 고쳐진 `data.sql`이 AWS DB에 실행될 유일한 기회를 영영 놓쳐버렸고, AWS DB는 영원히 텅 빈 상태로 남게 되었습니다.

### ③ 폭발: Fail-fast 방어 로직의 오작동 (`14f5262`)
* 이후 커밋에서, "DB 테이블이 이상하면 서버를 즉시 멈추게 하라"는 아주 강력한 안전장치(`DatabaseFixConfig`의 RuntimeException)가 추가되었습니다.
* **서버 구동 시 발생한 일:** 서버가 켜지면서 `payments` 테이블에 제약조건을 걸려고 했는데, **DB가 텅 비어서 테이블 자체가 없으니 서버가 스스로 목숨을 끊어버렸습니다 (크래시 발생).** 이것이 AWS에서 발생한 502/500 에러의 진짜 원인이었습니다.

### ④ 여진: 텅 빈 DB가 부른 AI 연동 400 에러
* 어찌어찌 로컬이나 다른 환경에서 서버가 켜졌더라도 문제가 발생합니다.
* 소비자 앱에서 "포트폴리오 1번 이미지 인페인팅 해줘!"라고 요청하면, 백엔드는 DB를 뒤집니다.
* 하지만 DB가 텅 비어있으니 포트폴리오를 찾을 수 없고, 결국 AI 서버(Render)로 `null` 값을 보내버립니다.
* **AI 서버의 반응:** "이미지가 없잖아!" 하며 400 에러를 뱉고 튕겨냅니다. (프론트엔드 콘솔에 찍힌 400 에러의 정체)

## 2. 🛠️ 해결 방안 (이번 PR에 포함된 내용)

이 모든 연쇄 폭발을 막기 위해 4가지 핵심 수정을 진행하여 `fix/aws-db-initialization` 브랜치에 올려두었습니다.

| 수정된 파일 | 수정 내용 및 이유 |
| :--- | :--- |
| **`application.yml`** | `sql.init.mode`를 임시로 `always`로 변경했습니다. **텅 빈 AWS DB에 드디어 완벽하게 고쳐진 `data.sql`을 부어 넣기 위한 핵심 조치**입니다. (배포 성공 후 반드시 다시 `never`로 돌려놓아야 합니다!) |
| **`DatabaseFixConfig.java`** | 수동 제약 조건(`ALTER TABLE`) 추가 시, 테이블이 존재하지 않는 에러(`1146`)가 발생해도 서버를 죽이지 않고 경고(`warn`)만 남기도록 **예외 처리를 유연하게 개선**했습니다. |
| **`build.gradle`** | 로컬 개발 환경에서 Java 21 버전을 사용할 때 빌드가 아예 안 되는 호환성 버그(Unsupported class file major version 69)를 고치기 위해 **Lombok 버전을 1.18.32로 명시적 고정**했습니다. |
| **`TokenProvider.java`** | JWT 시크릿 키가 Base64로 인코딩되어 있지 않은 환경(예: 로컬 테스트 등)에서도 에러를 뿜지 않고 일반 UTF-8로 안전하게 읽어올 수 있도록 **디코딩 예외 처리를 추가**했습니다. |

## 3. 📝 PR 작성 가이드 (복붙해서 사용하세요)

깃허브에서 Pull Request를 생성하실 때 본문에 아래 내용을 그대로 복사해서 붙여넣으시면 됩니다.

```markdown
## 💡 PR 목적 (이슈 원인 및 해결)
현재 AWS 환경에서 발생하던 500 에러 및 AI 서버 연동 400 에러의 근본 원인을 파악하고 방어 로직을 전면 수정했습니다.

### 🔍 원인 분석
1. **DB 초기화 누락:** 과거 `data.sql` 에러로 인해 AWS DB가 텅 빈 상태로 굳어졌으나, 이후 `sql.init.mode`가 `never`로 잠기면서 올바른 데이터가 주입되지 못했습니다.
2. **Fail-fast 크래시:** 텅 빈 DB에서 `DatabaseFixConfig`가 `payments` 테이블을 찾지 못해 서버 구동을 강제로 멈춰버렸습니다 (500 에러 발생).
3. **AI 서버 연동 에러:** 텅 빈 DB로 인해 포트폴리오 이미지를 조회하지 못해 AI 서버로 `null`이 전송되어 400 에러가 발생했습니다.

### 🛠️ 수정 사항
- **[임시] `application.yml` 변경:** 텅 빈 AWS DB에 초기 데이터를 세팅하기 위해 임시로 `sql.init.mode`를 `always`로 변경했습니다. (**※ 주의: 이번 배포 성공 직후 다음 커밋에서 무조건 `never`로 다시 롤백해야 합니다!**)
- **`DatabaseFixConfig.java` 개선:** `Table doesn't exist (1146)` 에러 발생 시 강제 크래시 대신 `warn` 로그만 남기도록 안전성을 강화했습니다.
- **`build.gradle` Lombok 버전 고정:** Java 21 환경에서 발생하는 `Unsupported class file major version 69` 빌드 에러를 해결하기 위해 버전을 1.18.32로 명시했습니다.
- **`TokenProvider.java` 예외 처리:** JWT 시크릿 키가 Base64 형식이 아닐 경우에도 안전하게 파싱하도록 예외 처리를 추가했습니다.
```
